1. 先把 policy 这个词讲清楚

在强化学习和机器人学习里，policy 可以先理解成一个函数：给定当前状态，它决定下一步做什么。写成最简单的形式就是 π(a | o, ℓ)：o 是观测，例如相机图像、激光雷达、车辆速度、机械臂关节角；ℓ 是任务指令，例如“把红色方块放到碗左边”或“前方施工，变到左侧车道”；a 是动作，例如机械臂末端位姿、移动底盘速度、汽车的轨迹点、转向和制动。

现实系统通常不是“一次输入、一次输出”就结束，而是闭环：

π(at|ot,l)
Policy pi maps observation and task to the next action.

1.1 policy 不等于“一个大模型回答一句话”

聊天模型的输出通常是字符串。机器人 policy 的输出必须落在接口上：动作维度要对，坐标系要对，速度和加速度要有边界，控制周期要满足实时性，碰撞和安全约束要能检查。因此，“让大模型参与 policy”有三个不同层次：

  1. 高层任务规划：把“收拾桌面”拆成拿起、移动、放下等子任务。
  2. 中层行为决策：在“跟车、变道、停车、绕行”等候选行为之间选择。
  3. 低层动作控制：输出连续的转向、速度、末端位姿或关节力矩。

很多论文只覆盖其中一层。把不同层次混为“端到端控制”会高估方法能力。Code as Policies 主要展示高层到中层的程序化策略表达；JevVLA 主要展示在已有机器人 policy 上做动作候选选择和连续动作修正。

2. 为什么会出现这两种范式

传统机器人系统往往把语言、感知、规划和控制拆开：语言模块解析命令，感知模块识别物体或车道，规划器生成路径，控制器跟踪路径。这种系统的优点是每个模块可以验证，缺点是遇到没见过的语言组合或新任务时，需要人工增加规则和接口。

端到端行为克隆或视觉—语言—动作模型则试图直接学习 观测 + 指令 → 动作。它们可以把视觉和语言知识带进策略，但也有两个问题：一是动作接口可能很难解释，二是当模型输出“语义上合理、几何上差一点”的动作时，失败可能很难诊断。比如机械臂“知道要把杯子放到盘子上”，不代表它算出了不碰撞的末端轨迹；车辆“知道应该变道”，不代表它选择的轨迹满足时距、曲率和横向加速度约束。

于是出现两种互补的想法：

  • 把大模型变成会表达不确定性的决策接口。软件提前定义候选项，模型只负责判断哪一个更合适，并把不确定程度交给上层路由。这就是 Jev 公开接口以及 JevVLA 所借鉴的方向。
  • 把大模型变成会写策略的程序生成器。模型不直接吐出一串连续控制量，而是生成能调用感知和控制函数的程序，用 if、for、while、几何运算和反馈循环表达任务。这就是 Code as Policies。

3. Jev：什么叫“结构化概率决策”

3.1 从自由文本变成有类型的输出

TypeSafe AI 对 Jev 的公开介绍把它描述为一种面向软件自动化的 System One model：输入仍可以是非结构化状态，但输出不是一段需要解析的自由文本，而是预先定义的类型化值，并且伴随概率和置信度。

最直观的例子是 Choice：软件先告诉模型只能在三个选项中选一个：

choice = {follow_lane, change_left, emergency_stop}

模型返回的不是“我觉得现在可以考虑向左变道”，而是类似：

choice: change_left
probabilities:
  follow_lane: 0.18
  change_left: 0.67
  emergency_stop: 0.15
confidence: 0.54

这里至少有三层信息：

  • 结构：输出一定属于预先定义的选项，软件不必从自然语言中猜意图。
  • 概率分布：不仅告诉你最大项，也告诉你第二项是否接近；这可以用于候选排序和风险路由。
  • 置信度：概率是否尖锐、模型是否犹豫，可以触发“减速、扩大安全距离、交给更强模型或请求人工确认”。

上面的数值只是教学假设，不是 Jev API 实测返回。还要把“最大选项概率”“分布是否尖锐”和接口里的 confidence 字段分开：三者可以相关，但不能在没有定义和校准证据时视为同一个量。Jev 的公开示例主要使用结构化问题与状态文本；本报告不把它描述成已经直接接收原始摄像头/雷达的通用驾驶模型。多模态系统可以先用感知模块把图像转成事实，再把事实交给决策模块。

Score 则适合把质量写成有序等级，例如“轨迹安全性：危险、可接受、保守、优越”。它返回各等级的概率以及一个期望分数。注意：这不是凭空产生了物理安全证明；它只是把模型的判断包装成软件可以消费的结构。

E[s]=∑k=0K−1kpk
Expected score is defined by the ordered levels and their probabilities.

这里的数字表示“模型在事先定义的评分等级上的期望”，不是以秒、米或碰撞频率测量的物理量。若等级顺序和描述不清楚，分数本身就没有稳定含义。

来源定位：[S01] 官方介绍；[S02] Choice 文档；[S03] Score 文档。驾驶选项和数值均为教学示例。

3.2 为什么说“概率决策”比“分类”更适合机器人

表面上看，Choice 很像分类器。但机器人场景更在意“备选项之间的相对关系”和“不确定时怎么办”。例如一个移动机器人在走廊里遇到行人：

  • 选项 A：保持路径，概率 0.45；
  • 选项 B：向左绕行，概率 0.40；
  • 选项 C：停止等待，概率 0.15。

如果只取 argmax，系统会保持路径；如果同时看置信度和概率差，系统会发现 A/B 很接近，于是可以放慢速度、扩大观测窗口，或者交给一个带碰撞验证的局部规划器。结构化概率的价值，往往不是让模型“一次选对”，而是允许系统根据不确定性改变行为。

这并不是说传统分类器做不到：分类器同样可以给出全量概率，也可以做校准和拒答。Jev 的特点在于面向软件工作流的任务/类型接口设计，而不是“第一次让分类具有概率”。候选集还会限制模型：如果只有“向左、向右”，却没有“停车”，分布归一化也不会自动发现那个缺失的正确动作。

3.3 JevVLA 如何把这个思想落到机器人动作上

JevVLA 的问题更具体：已有的 VLA policy 已经能提出动作，但动作可能不够好。能否冻结基础 policy，只训练一个很小的“动作偏好适配器”？

它把观测、语言和基础策略特征编码成上下文 c，把动作编码成 z，再用一个标量能量函数表示偏好：Eθ(c,z)=1/2 zᵀQθ(c)z−bθ(h)ᵀz−Rθ(h,fᵃθ(z))。

Eθ(c,z)=12zTQθ(c)z−bT(c)z−Rθ(c,fθ(z))
The context-conditioned scalar represents relative action preference.

直觉是：二次项提供一个依赖上下文的“地形”，线性项把偏好区域推向某一侧，低秩项让不同动作坐标之间产生耦合，残差网络再补上非线性偏好。论文明确说，这个 energy 是学习到的 preference potential，不是物理学意义上的能量。

离散候选选择可以抽象成：

候选动作 A = {a₁, a₂, …, aₖ}
score(aᵢ) = base_prior(aᵢ) - β · energy(c, aᵢ)
执行 argmaxᵢ score(aᵢ)

连续动作则利用负梯度：a′ = Π(a + ηgθ(c,a))，其中 gθ(c,a) = −∇ₐEθ(c,a)，Π 表示动作边界投影。

z′=ΠB(z+ηgθ(c,z)),gθ=−∇zEθ
A local gradient update is projected back into the action bounds.

3.3.1 从训练数据到推理：究竟学了什么

训练阶段，基础 VLA 参数冻结；系统收集执行成功/失败、专家修正或示范派生的偏好。对离散候选，可以把更好的候选作为更应被选中的监督目标；对连续动作，则让能量梯度接近“从当前动作朝更优动作走”的局部方向。二者共享的是函数结构，并不意味着把所有任务混在一起训练一个万能权重。论文的各个基准独立训练适配器。

pi=eli∑jelj
候选 logits 归一化为集合内的相对概率；无效项必须先屏蔽。

这个 softmax 公式是帮助阅读候选选择的简化式：基础策略先验与能量一起形成相对 logit；无效候选要先屏蔽。它得到“这个集合里哪个更好”的归一化分布，并没有得到“每条轨迹在真实世界中会成功多少次”的概率。连续修正也只是局部建议；动作裁剪能约束每维幅度，但不自动保证整段轨迹无碰撞。

Lpref=−∑iqilogpi,Lgrad=∥gθ−g∗∥2
简化教学式：一项约束候选偏好，另一项约束局部动作修正方向；具体损失随监督来源而异。

交叉熵中 q 是训练目标偏好分布；梯度匹配比较模型的局部方向与监督方向。它们不是要求读者实现的全部损失清单：论文还区分不同基准可用的结果排序、专家纠正、去噪及混合目标。对初学者，最重要的是把“训练一个评分函数”和“推理时用它来选/修动作”分开。

来源定位：[S04] JevVLA §3 的能量、候选比较与梯度学习；上式中的候选分布和两项损失为教学合并表达，具体配置以论文各基准协议为准。

3.4 用具身机器人例子理解它

设机械臂 VLA policy 给出了三个“把橙色块放入粉色碗”的候选动作。三个动作语义都正确，但候选 1 的抓取点偏左，候选 2 可能碰到旁边的块，候选 3 的路径更短。Jev-like 适配器可以利用执行反馈，把成功候选的偏好质量提高，把失败候选的质量降低；推理时不需要重写整个 VLA，只需在这三个动作之间重新排序。

对于连续动作块，例如机械臂连续输出未来 8 个时间步的位移，适配器可以在每个动作块附近计算梯度，并做一个有界的微调。它更像“把基础策略的动作推到一个更好的局部区域”，而不是从零生成一条完整轨迹。

3.5 放到自动驾驶里应该怎么理解

这里必须区分“论文直接证明的内容”和“合理的架构映射”。JevVLA 论文的实验是 MetaWorld、VIMA、LanguageTable、LIBERO Plus 和 CLIPort 等机器人操作基准，并不是自动驾驶基准。因此，下面是工程上的类比，不是原论文的自动驾驶结果。

自动驾驶可以把每一帧的行为决策写成候选集合：

候选行为 = {保持车道, 左变道, 右变道, 减速跟车, 停车}

Jev-like 模块可以输入摄像头/雷达/地图/历史轨迹，输出候选行为的相对概率和置信度。对更连续的轨迹生成，也可以给若干候选轨迹打分，或者对一个已有轨迹做局部修正。这样做的意义是：

  1. 把“模型犹豫”显式化，而不是让它藏在一串连续控制量里；
  2. 允许上层用概率差、置信度和风险阈值做路由；
  3. 保留传统规划器对碰撞、动力学、道路规则的硬约束。

但不能把这个分数直接叫作“安全概率”。除非训练数据、校准方法和验证协议都支持，否则它只是模型学到的相对偏好或置信度，不能替代形式化安全检查。

4. Code as Policies：什么叫“把知识组织为可执行程序”

4.1 从“回答步骤”到“生成控制程序”

Code as Policies 的核心观察是：代码生成模型已经学过很多程序结构。与其让 LLM 只输出“第一步拿起方块，第二步移动到碗旁边”，不如把可用的感知和动作 API 交给它，让它生成一段能真正调用这些 API 的程序。

例如系统提供：

get_obj_pos(name)                  # 返回物体位置
put_first_on_second(obj, target)   # 执行抓取与放置
move_to(x, y, speed=...)            # 移动底盘或机械臂

用户说“把红块放到蓝碗左边一点”，模型可以组织成：

red = get_obj_pos("red block")
blue_bowl = get_obj_pos("blue bowl")
target = blue_bowl + np.array([-0.10, 0.0])
put_first_on_second("red block", target)

这里的“知识”不是一个藏在权重里的答案，而是被组织成：调用哪个感知函数、怎样计算几何关系、何时循环、何时重新感知、最后调用哪个控制 primitive。

4.2 为什么代码能表达更丰富的 policy

自然语言计划通常很难精确表达反馈和条件：

一直向前走，直到看到障碍物；如果左侧有空间就左绕，否则停车。

程序可以直接表达：

while not seen("obstacle"):
    move_forward(speed=0.4)
if free_space("left") > 1.2:
    turn_left(angle=35)
else:
    brake()

Code as Policies 论文展示的能力包括：用感知输出作为输入、参数化控制 primitive、做空间几何推理、组合多步行为、使用 NumPy/Shapely 等库，并用层级代码生成递归定义未定义函数。它也强调局限：当 API 变化很大时，模型的跨 embodiment 适配会变得脆弱。

4.3 层级代码生成为什么重要

复杂任务往往不是一次生成一个巨大函数，而是先生成高层函数，再遇到未定义函数时继续向下生成。例如：

move_blocks_to_matching_bowls()
  ├── find_blocks()
  ├── find_matching_bowl(block)
  └── put_first_on_second(block, bowl)

这种方式类似“程序化的任务分解”。每一层都可以有自己的提示和 API 边界，也更容易把感知解析、几何变换和执行动作组合起来。

4.4 具身机器人例子

在桌面操作中，Code as Policies 适合开放式组合任务：识别“所有在红碗左边的方块”，计算每个方块的新位置，然后循环调用抓取和放置。它的优势不是每个 primitive 都比专门控制器更好，而是能把已有 primitives 组合成数据集没有逐一标注的新任务。

在移动机器人中，策略代码可以根据底盘 API 的不同改变执行顺序。例如全向底盘可以分别调用向上/向右移动；单向底盘则需要“前进—转向—前进”的组合。这个例子说明代码策略天然携带 embodiment 的动作接口，但也说明它依赖 API 描述准确且稳定。

4.5 具身机器人相关工作：从技能选择到程序执行

把这两条路线放回具身机器人研究谱系，会更容易看出它们分别解决哪一个瓶颈。SayCan 的基本思路是让语言模型提出“应该做什么技能”，再用环境中的 affordance/value 信号判断“当前能不能做”；它解决的是语言意图与可执行技能之间的落地，但输出仍主要是技能序列，不是带完整概率接口的动作评分器，也不是任意 Python policy。

RT-2 则把视觉—语言知识和机器人动作放进同一个 VLA policy，把动作编码成模型可以预测的 token。它更接近“直接学习观测到动作”的端到端路线：模型能把互联网视觉语言知识迁移到机器人动作，但动作接口、候选比较和失败时的置信度路由并不是它的主要抽象。

VoxPoser 更接近程序化/可组合的一侧：语言模型生成可组合的 3D value map 或约束表达，再由传统规划与控制模块把这些表达转成动作。它说明“让大模型写中间表示或规划程序”比让大模型直接输出关节力矩更容易保留几何约束；但它仍不是 Code as Policies 的逐字复现，也不是 JevVLA 的能量适配器。

因此，可以把具身机器人中的几条路线粗略排成这样：

路线 大模型主要产物 最接近的 policy 位置 关键边界
SayCan 技能选择/技能序列 高层任务规划 需要 affordance/value 过滤可执行性
RT-2 动作 token / VLA 动作 端到端动作 policy 不以显式候选概率和程序结构为中心
VoxPoser 3D value map、约束或规划表达 中层规划表示 最终动作仍由规划器/控制器落地
JevVLA 候选动作排序、连续动作局部修正 已有 policy 上的适配层 依赖基础 policy 提供候选，不是从零任务规划
Code as Policies 可调用感知与控制 API 的程序 高层到中层策略编排 代码执行必须有白名单、沙箱和验证

这张表的重点不是给方法排“先进程度”，而是提醒读者：“大模型参与 policy”可以发生在技能选择、动作生成、规划表示、候选评估和程序编排等不同位置。

4.6 放到自动驾驶里应该怎么理解

自动驾驶中的“可执行程序”可以是高层行为脚本或场景策略，而不是让 LLM 直接生成底层转角。例如：

if construction_zone_ahead() and lane_is_clear("left"):
    request_lane_change("left", reason="construction")
elif lead_vehicle_is_slow() and safe_follow_distance() > threshold:
    plan_overtake()
else:
    keep_lane_and_adjust_speed()

它的价值在于把交通规则、任务条件、语义场景和系统 API 组织起来；真正的轨迹生成、碰撞检查和车辆控制仍应由经过验证的模块执行。换句话说，Code-as-Policy 更像“行为层/任务层的程序编译器”，不等于“让聊天模型直接掌舵”。

5. 自动驾驶相关工作：已有研究各自站在哪一层

自动驾驶领域已经出现了几种把语言模型接入驾驶 policy 的方式，但它们并不等价于 Jev 或 Code as Policies。下面的对照是为了帮助定位“相似思想”，不是把这些论文改写成核心方法的直接实验。

5.1 LanguageMPC：语言模型做高层决策，MPC 做可执行控制

LanguageMPC 把 LLM 放在复杂驾驶场景的决策位置，使用认知路径帮助模型处理高层语义，再把语言模型的决策翻译成驾驶命令，并通过参数矩阵适配与低层控制器衔接。论文还讨论了文本驾驶风格、施工区域和多车辆协同等场景。

它与两条范式的关系是：一方面，它与 Jev-like 路线相似，都把大模型放在“选择/决策”而不是直接输出每个底层控制周期的转角；另一方面，它并没有把 Jev 的 Choice/Score 概率接口直接搬进来，因此不能说它已经实现了结构化概率决策。更准确的说法是：它展示了高层语言决策 + 传统控制器执行的工程分层。

5.2 GPT-Driver：把轨迹坐标改写成语言建模问题

GPT-Driver 走的是另一条路：把运动规划的输入和输出表示成语言 token，让 GPT-3.5 生成由坐标点描述的驾驶轨迹，并用 prompting–reasoning–finetuning 激发数值推理能力。它在 nuScenes 上评估轨迹规划、泛化与可解释性。

这更像“让语言模型直接生成结构化轨迹序列”，而不是 Code-as-Policy：输出是轨迹数据，不是包含 if/for 和 API 调用的程序；也不是 Jev-like scorer，因为它的主任务是生成轨迹，而不是对外部候选集合返回概率与置信度。它代表了“把连续规划序列语言化”的方向。

5.3 Agent-Driver：工具调用、记忆和反思组成驾驶智能体

Agent-Driver 在传统感知—预测—规划管线外加入工具库、认知记忆和推理引擎。工具通过函数调用提供给 LLM，推理引擎覆盖任务规划、运动规划和自反思，并在 nuScenes 的开环与闭环任务上评估。

它与 Code-as-Policy 的相似点最明显：二者都把能力组织成可调用工具，并允许模型组合多步任务逻辑。区别在于，Agent-Driver 更像一个带记忆和反思的语言智能体系统；Code as Policies 的核心论点则是让策略本身以可执行程序的形式表达。前者不必生成一段完整 Python policy，后者也不自带驾驶记忆系统。

这里需要把评估位置说精确：nuScenes 对应开环轨迹规划；闭环评估使用 CARLA 的 Town05-Short。开环相当于“在录制场景中写答案，再和参考轨迹比较”，闭环相当于“执行了答案后，场景会随之变化，再继续驾驶”。前一种结果好，不自动推出后一种也好，更不直接推出实车安全。

5.4 LangProp：让生成代码在数据反馈中迭代优化

LangProp 进一步把“代码就是 policy”放进优化闭环：LLM 先生成代码，系统在输入—输出数据集上评估代码表现、捕获异常，再把结果反馈给 LLM，让它继续改进。论文在 CARLA 上给出了自动驾驶代码策略优化的 proof of concept。

这与 Code as Policies 的关系很像“生成器”与“优化器”的关系：原始 Code-as-Policy 关注能否从语言、示例和 API 生成可执行程序；LangProp 关注生成出来的程序能否在指标和数据反馈下继续优化。因此它仍然不是 Jev-like 的候选概率接口，但为驾驶策略代码增加了可度量的迭代改进环节。

初学者可以用一个问题来区分它们：模型输出的是“选哪个”、“生成一条轨迹”、“调用哪些工具”，还是“写一段可循环执行的程序”？ 这四种输出形式看起来都叫“policy”，但软件接口、验证方式和安全边界完全不同。

7. 两者能不能组合

能，而且组合后比单独使用更符合机器人和自动驾驶的工程结构：

  1. Code-as-Policy 负责把语言任务转成可执行的高层流程，决定要调用哪些感知、候选生成和控制接口。
  2. 候选生成器/基础 policy 负责提出若干轨迹、动作块或行为选项。
  3. Jev-like 评估器负责比较这些候选，输出相对偏好、概率和置信度，必要时对连续动作做小幅修正。
  4. 规划器和安全层负责碰撞、动力学、法规、控制频率和不可违反约束。
  5. 控制器把通过检查的轨迹变成转向、制动、末端位姿或关节控制。

8. 论文和代码到底证明了什么

8.1 Jev / JevVLA 的证据边界

TypeSafe AI 的 Jev 页面和文档证明了公开的接口理念：Choice 返回选项概率与 confidence，Score 返回等级概率、分数与 confidence。它们没有公开一个足以让外部复现完整 Jev 内部训练过程的论文级模型细节。因此，不能把 Jev 的产品介绍写成“已经证明概率一定校准”。

JevVLA 是一篇明确的机器人论文和一个公开代码仓库。论文给出了能量函数、偏好损失、梯度匹配、动作选择和连续引导公式；代码中可以核对：UnifiedQuadraticEnergy.raw_energy 计算条件二次项和 residual，candidate_probabilities 对候选 logits 做 softmax，select_candidate 执行候选选择，correct_action 通过自动微分得到连续修正方向。

它的实验覆盖五个机器人操作基准，报告相对于匹配 Direct 基线的成功率提升。但这些结果只支持“这种轻量能量适配器在这些机器人设置中可行”，不支持“它已经是自动驾驶通用决策器”。

8.2 Code as Policies 的证据边界

Code as Policies 论文和官方项目页证明了：代码生成 LLM 可以根据自然语言、few-shot 示例和 API 提示生成机器人策略程序，并在桌面操作、形状绘制、移动机器人等设置中展示空间几何、反应式控制和跨 embodiment 示例。官方仓库目前以 Colab notebooks 和提示文件为主，读者应把它看作研究演示/实验材料，而不是一个已经封装好的安全生产运行时。

论文还明确指出，跨 embodiment 的适配对 API 描述很敏感；当动作接口变化很大时，现有 LLM 可能不够稳健。这个边界对自动驾驶尤其重要：车辆的控制 API、坐标系、时延和法规约束不能只靠自然语言提示维护。

9. 对初学者最重要的四个判断

判断一：结构化概率不是“模型更聪明”，而是“接口更适合软件”

普通 LLM 也可以被要求输出 JSON，但如果模型本质上仍在生成字符串，解析错误、字段缺失和过度自信仍可能存在。结构化决策范式的重点是训练和接口都围绕固定类型、候选分布和置信度设计，让软件有稳定的消费方式。

判断二：可执行程序不是“把模型输出直接 exec”

Code-as-Policy 的思想是让代码表达 policy，但工程上必须加沙箱、白名单 API、类型/语法检查、资源限制、超时、仿真回放、碰撞检查和人工审批。研究中的 exec 示例是为了验证生成程序，不能直接视为生产部署方案。

判断三：候选评估和程序生成解决的是不同瓶颈

如果系统已经有一个不错的候选轨迹生成器，但总在几个候选之间选错，Jev-like scorer 可能更合适；如果系统缺的是任务组合、规则表达和多步 API 编排，Code-as-Policy 更合适。前者不自动创造候选，后者不自动保证候选安全。

判断四：自动驾驶更可能采用混合式，而不是二选一

驾驶系统通常需要同时处理开放语义和严格物理约束。更现实的组合是：大模型负责理解任务和场景、产生结构化意图或候选行为；专门模型/规划器生成并验证轨迹；概率决策模块负责排序、置信度与降级；控制器执行最终动作。

11. 学完后如何继续读论文

推荐按下面顺序回看：

  1. 先读 Code as Policies 的 Introduction，理解它为什么不满足于“LLM 只做技能序列规划”。
  2. 再读 Jev 的 Choice/Score 文档，亲自看一个结构化概率输出长什么样。
  3. 再读 JevVLA 的第 3 节，把 Eθ(c,z)、候选选择和动作梯度放回 VLA policy 适配场景。
  4. 最后打开代码 crosswalk，沿着 raw_energy → logits → select_candidate/correct_action 追一遍调用链。

如果只记住一个总图：Code-as-Policy 负责“把任务写成能执行的流程”，Jev-like 负责“在候选决策中表达偏好和不确定性”；具身机器人和自动驾驶的安全层负责“什么动作最终允许执行”。

附录 A · 从问题追到代码

论文问题台账与源码回答

Q1：Jev 到底是什么，是否就是 JEPA？

答案：不是。 本报告中的 Jev 指 TypeSafe AI 公开的 System One model；JevVLA 论文引用的是 Jev 的公开决策接口思想。JEPA 是另一类联合嵌入预测架构，不能因为拼写相近而混用。

证据： TypeSafe AI 的 Jev 介绍页；JevVLA 论文第 1 节明确写的是 “Jev’s structured, probabilistic decision interface”。

Q2：JevVLA 是否复现了 Jev 的内部模型？

答案：不是。 论文明确把 Jev 的联系限定在决策接口层；动作编码、条件二次能量、偏好损失和梯度引导都是 JevVLA 自己的设计。

Q3：JevVLA 的“概率”从哪里来？

答案： 对候选动作的 logits 做 softmax；logits 可以融合基础策略 prior、energy 得分、Direct margin 和有效候选 mask。推理时 select_candidate 取最大项；概率分布用于比较和分析，执行本身可以只需要 argmax。

Q4：连续动作为什么能用同一个模型？

答案： 标量函数的函数值可以比较动作，函数对动作的梯度提供局部修正方向。correct_action 对输入动作启用梯度，得到方向后乘 gain、做 coordinate mask、component clip 和上下界裁剪。

Q5：Code as Policies 的“知识”具体存在哪里？

答案： 一部分在代码生成模型的预训练能力中，另一部分被显式放进 prompt 的 API、示例和当前感知状态中；最终知识以函数调用、几何计算、条件和循环的形式落进生成程序。

Q6：Code as Policies 是否等于安全地执行任意代码？

答案： 不等于。论文/Notebook 使用受限执行演示能力，生产系统需要沙箱和白名单。尤其自动驾驶不能让生成代码直接绕过碰撞、动力学和法规检查。

Q7：这两条路线哪个更适合自动驾驶？

答案： 不是单选。开放式场景理解和行为编排更接近 Code-as-Policy；候选行为/轨迹排序、不确定性路由和有限动作修正更接近 Jev-like。最终控制仍需要专门规划与控制栈。

JevVLA

JevVLA 的实验问题不是“Jev 能不能聊天”，而是：在冻结基础 VLA 的前提下，一个约 8 万参数的能量适配器能不能改善动作选择和连续动作引导。五个基准覆盖两种接口：CLIPort/VIMA 更接近有限候选选择，LanguageTable/MetaWorld 等包含连续动作修正或 action chunk guidance，LIBERO Plus 同时考察复杂操作。

论文报告的测试集增益为：MetaWorld MT50 +1.28 个百分点、VIMA +2.31、LanguageTable +1.60、LIBERO Plus +1.52、CLIPort +1.28。这里的正确阅读方式是“相对于各自 Direct 对照的成功率差”，不是跨基准可直接比较的绝对能力排名。

论文还做了结构消融：去掉 quadratic、residual、low-rank coupling 会带来不同程度下降；偏好标签打乱、特征打乱和随机初始化也会损失性能。这些实验支持“学习到的上下文—动作偏好关系确实有用”，但不能证明概率已经完美校准，也不能证明能量分数具有物理意义。

Code as Policies

Code as Policies 关注的是生成程序是否能表达更复杂的机器人策略。实验/Notebook 覆盖 HumanEval、反应式 toy controller、形状绘制、桌面操作和移动机器人/移动操作场景。论文强调的结果包括：生成代码可以使用感知 API 和控制 primitive，进行几何推理，处理未见过的指令组合，并用层级代码生成补全未定义函数。

这些实验更像“程序表达能力与零样本/少样本组合能力”的证明，不是对任意机器人平台安全部署的证明。代码的正确性、API 适配和执行安全仍是系统集成问题。

自动驾驶解读

两篇核心来源都不能被表述为自动驾驶实验论文。因此自动驾驶部分只给出架构映射：

  • Jev-like：对有限行为/轨迹候选做相对评估、输出置信度、决定是否降级或交给安全规划器。
  • Code-as-Policy：把场景语义和规则编译成高层行为 API 调用。
  • 规划器/控制器：负责硬约束和实时执行。
