0. 先给一个全局地图：Qwen-VL 系列到底在解决什么

这一系列 Qwen-VL 模型可以先按一句白话理解：它把图片、视频变成一串“能被大语言模型读懂的视觉 token”，再让 Qwen 文本模型像读一段特殊文本一样读这些 token。真正难的不是“接一张图进去”，而是三件事：第一，任意大小图片怎么变成长度可控的 token；第二，视觉 token 的空间/时间位置怎么编码；第三，训练时如何让语言模型学会把这些 token 当作真实视觉证据，而不是把它们当作普通噪声。

从 Qwen2-VL 到 Qwen2.5-VL，再到 Qwen3-VL，主线可以概括成：先把动态分辨率和 M-RoPE 跑通；再把长视频、窗口注意力、动态 FPS、坐标输出和 agent 能力补强；最后把 DeepStack、Interleaved-MRoPE、Thinking 模式、MoE 大模型和更长上下文堆上去。它不是每一代都推翻前一代，而是在同一条“视觉 token 接入 LLM”的工程主线上不断修补瓶颈。

初学者容易误解的一点是：Qwen-VL 不是 CLIP 加一个聊天模型那么简单。CLIP 式视觉编码器通常输出一个图像级或局部语义表示，而 Qwen-VL 需要保留足够细的局部结构，以支持 OCR、表格、目标定位、视频时间推理和多图对比。因此它的视觉塔、PatchMerger、processor 的占位符展开、M-RoPE 的位置索引，都属于核心模块，而不是边角料。

1. 一条样本从输入到生成答案：最小闭环

先不看论文术语，只看一次推理的流水线：用户输入一段 chat message，里面可能有文字、图片、视频路径。`processor` 会把图片/视频预处理成 `pixel_values`，同时把文本里的 `<|image_pad|>` 或 `<|video_pad|>` 按视觉 token 数量扩展成一串占位符。模型前向时，视觉塔先把 `pixel_values` 编码成 `image_embeds` / `video_embeds`，再用 mask 把这些视觉 embedding 填回 LLM 的 token embedding 序列。

这个设计的工程好处很朴素：LLM 不需要额外开一个复杂 cross-attention 模块，而是看到一串已经投影到隐藏维度的“特殊 token”。白话说，就是把图片先翻译成一段模型内部语言，然后插进提示词里。代价是 token 数和位置必须严格对齐，错一个 token 都会直接报错或产生错位理解。

messages -> processor.apply_chat_template
images/videos -> image_processor/video_processor -> pixel_values + grid_thw
text placeholders -> repeat <|image_pad|> or <|video_pad|> by prod(grid_thw) // merge_size^2
vision tower -> image_embeds/video_embeds
LLM input embeddings -> replace placeholder positions with visual embeddings
language model -> next token generation

源码里可以看到非常硬的对齐检查：如果 image token 数和 image feature 数不一致，就抛出类似 “Image features and image tokens do not match” 的错误。这不是小题大做，因为视觉 token 与文本位置一旦错位，模型后面的 RoPE 位置、attention mask 和生成语义都会一起错。

`grid_thw` 是理解整套系统的钥匙。它表示视觉特征网格的时间、宽高三维尺寸：`T` 是帧或时间片数，`H/W` 是 patch 网格高宽。后面所有 token 数、位置编码、窗口切分、视频时间索引都围着它转。很多源码读不懂，根本原因就是没有先把 `grid_thw` 当成中心变量。

2. 动态分辨率：不是“不缩放”，而是“按预算缩放”

Qwen2-VL 官方称为 Naive Dynamic Resolution。白话解释：输入图片不用硬裁成固定 224×224 或 448×448，而是保留接近原始宽高比的尺寸，再把长宽调整到 patch/merge 需要的倍数范围内。这样文档截图、长图、表格、海报、多栏文本能保留更多细节。

但它绝不是无限吃原图。processor 仍然会有 `min_pixels`、`max_pixels`、patch size、merge size 等约束。模型实际看到的是经过预算控制后的网格。公式上，图像最终进入 LLM 的视觉 token 数大致是：

Nvision≈T×Hgrid×Wgridmerge_size2N_{vision} \approx \frac{T \times H_{grid} \times W_{grid}}{merge\_size^2}Nvision​≈merge_size2T×Hgrid​×Wgrid​​

对于 Qwen2/Qwen2.5 常见设置，patch size 为 14、spatial merge size 为 2。单图在视觉塔 patch 化后是 `H/14 × W/14`，再每 2×2 合并一次，所以最终 LLM 视觉 token 大约是 `H×W/784`。这解释了为什么大图很贵：分辨率翻倍，token 数按面积涨。

工程上最重要的 tradeoff 是：动态分辨率提高了 OCR 和细粒度定位能力，但上下文预算、显存和 attention 成本也会变大。实际部署时往往要给不同场景设不同图片预算：普通照片可以低一些，文档/表格/代码截图需要更高，视频要更谨慎，因为视频还多了时间维度。

3. Qwen2-VL：把视觉 token 稳定接进 Qwen2

Qwen2-VL 的骨架可以拆成四块：输入 processor、视觉 transformer、PatchMerger、Qwen2 语言模型。processor 负责把外部图片/视频变成张量和占位符；视觉 transformer 把 patch 序列做自注意力；PatchMerger 把 2×2 空间邻域压到一个 LLM token，并把维度投影到语言模型隐藏维；最后语言模型在同一 token 序列里处理文本和视觉 token。

源码里 `Qwen2VisionTransformerPretrainedModel.forward` 的顺序很直：`patch_embed -> rot_pos_emb -> blocks -> merger`。这说明 Qwen2-VL 的视觉侧没有先做一堆花哨跨模态融合，它先把图像/视频编码成一个相对干净的视觉 token 序列，再交给语言模型统一处理。

`PatchEmbed` 的任务是把图片切成 patch 并线性化。对于视频，它使用 temporal patch 的概念，让时间维也进入 patch。知乎源码解读里提到图像会按类似两帧的形式处理，这是因为统一图像/视频路径时需要一个时间维；对单图而言，时间只是占位，真正主要区分还是高宽二维。

`PatchMerger` 很关键。它不是简单平均池化，而是把若干相邻 patch 的隐藏向量拼接后经过 MLP/投影，输出 LLM 维度。白话说：视觉塔内部 token 还比较细，Merger 把一小块局部视觉信息打包成一个语言模型能消费的 token。这个设计兼顾两个目标：保留局部结构，又不要让 LLM 被过多视觉 token 淹没。

Qwen2-VL vision forward:
hidden_states = patch_embed(pixel_values)
rotary_pos_emb = rot_pos_emb(grid_thw)
for block in vision_blocks:
    hidden_states = block(hidden_states, cu_seqlens, rotary_pos_emb)
image_embeds = merger(hidden_states)
inputs_embeds[image_token_mask] = image_embeds

训练阶段可以从职责上理解：第一阶段让视觉塔和语言模型对齐基础视觉语义；第二阶段加入更多多模态任务让模型学会 OCR、定位、图文推理等；第三阶段通过指令数据让模型像聊天助手一样输出。不要把训练阶段只看成数据量堆叠，它本质上是在逐步教模型“看见、对齐、服从指令”。

4. M-RoPE：为什么视觉位置不能只用一维 token 序号

普通文本模型的 RoPE 很简单：第 0 个词、第 1 个词、第 2 个词……一维递增即可。图像不一样。如果把一张图按扫描顺序拉平，模型虽然知道 token 先后，却天然不知道“同一行相邻”和“跨行相邻”的几何差异。视频更麻烦，还要知道帧时间。M-RoPE 就是给 token 补上多维位置感。

Qwen2/Qwen2.5 的 `get_rope_index` 会构造三路 position ids：文本 token 三路都用同一个一维位置；图像 token 用 `[t, h, w]`，其中单图的时间维通常只是 0 或 1 个逻辑时间片；视频 token 则同时有时间、高、宽。最终这三路位置进入 RoPE，让 attention 的 q/k 旋转角带上空间/时间信息。

白话比喻：普通 RoPE 像给书页每个字标一个页内序号；M-RoPE 像给地图上的每个格子标“第几帧、第几行、第几列”。同样是一串 token，模型内部能感知到二维/三维邻近关系。

positionvision=(t,h,w),NLLM_vision=T⋅H⋅Wmerge_size2position_{vision} = (t, h, w), \quad N_{LLM\_vision}=\frac{T\cdot H\cdot W}{merge\_size^2}positionvision​=(t,h,w),NLLM_vision​=merge_size2T⋅H⋅W​

`rope_deltas` 是另一个容易忽略的工程细节。多模态 token 的 position ids 不是普通连续 0..N，它会因为图像/视频网格插入而产生和文本序列长度的差值。缓存生成时如果不记录这个 delta，后续增量解码的位置会错。

5. Qwen2.5-VL：窗口注意力、动态时间和结构化输出

Qwen2.5-VL 最核心的工程改动之一是视觉塔 Window Attention。Qwen2-VL 视觉侧更接近对每个图/视频样本做完整注意力，而 Qwen2.5-VL 会先按窗口重排 token，大多数层在窗口内做 attention，少数指定层仍做全局 attention。这样可以降低长图、长视频的视觉侧计算成本，同时让少数全局层负责跨窗口信息交换。

源码里 `get_window_index` 会把 LLM 视觉网格按窗口切块，padding 不足的窗口位置为 -100，再生成 `window_index` 和 `cu_window_seqlens`。forward 时先用 `window_index` 重排 hidden states 和 rotary embedding；每层根据 `fullatt_block_indexes` 决定用全局 `cu_seqlens` 还是窗口 `cu_window_seqlens`；最后用 `reverse_indices` 把 token 顺序还原。

Qwen2.5-VL window attention:
window_index, cu_window_seqlens = get_window_index(grid_thw)
hidden_states = hidden_states[window_index]
for layer_num, block in enumerate(blocks):
    if layer_num in fullatt_block_indexes:
        cu = cu_seqlens          # global attention
    else:
        cu = cu_window_seqlens   # local window attention
    hidden_states = block(hidden_states, cu)
hidden_states = merger(hidden_states)
hidden_states = hidden_states[argsort(window_index)]

第二个关键改动是视频时间。Qwen2.5-VL 引入 `second_per_grid_ts`，把视频 grid 的第 t 个时间片映射到真实秒数，再乘以 `tokens_per_second` 得到时间位置。也就是说，它不是只知道“第 0 帧、第 1 帧”，还尽量知道这些帧隔了多少真实时间。对长视频问答、事件顺序、定位某一秒发生了什么，这很重要。

第三个改动是面向真实产品的输出形态。官方博客强调 Qwen2.5-VL 能更好地产生 structured outputs、QwenVL HTML 等结果，并具备更强 grounding 能力。白话说，模型不只是能“看懂”，还要能按机器可消费的格式回答，例如框坐标、JSON、HTML、UI 操作指令。这是从 demo 能力走向 agent/自动化能力的关键一步。

6. Qwen3-VL：DeepStack、Interleaved-MRoPE、timestamp 和 MoE

Qwen3-VL 的官方仓库列出了 Dense 和 MoE 两条线：Dense 有 2B/4B/8B/32B，MoE 有 30B-A3B 和 235B-A22B，并区分 Instruct 与 Thinking。Instruct 更像直接回答型助手，Thinking 更强调复杂推理链路。对用户来说，这意味着选模型时不是只看总参数，还要看激活参数、上下文长度、是否需要推理过程、部署显存和吞吐。

DeepStack 是 Qwen3-VL 最值得重点理解的结构之一。传统做法通常只把视觉塔最后一层输出交给 LLM；DeepStack 会从视觉塔的若干中间层取特征，经多个 merger 变成 `deepstack_visual_embeds`，再在语言模型前几层把这些视觉特征加回对应视觉 token 位置。白话说：不是只把“最终压缩版视觉理解”递给语言模型，而是把早中层的细节也沿着语言模型浅层注入，减少小字、局部结构、图表细节在最后层被过度抽象的问题。

Qwen3-VL DeepStack idea:
for layer_num, vision_block in enumerate(vision_blocks):
    hidden_states = vision_block(hidden_states)
    if layer_num in deepstack_visual_indexes:
        deepstack_feature_lists.append(deepstack_merger(hidden_states))

language_model(...,
    visual_pos_masks=visual_token_positions,
    deepstack_visual_embeds=deepstack_feature_lists)

Interleaved-MRoPE 解决的是三维位置频率分配问题。旧式 chunked M-RoPE 更像把频率维度切成一段给 T、一段给 H、一段给 W。Qwen3-VL 源码里的注释明确说它把 `[TTT...HHH...WWW]` 重排为 interleaved 形式，例如 `[THTHWHTHW...]`，以保持频率连续性。白话说，就是不要让时间、行、列各自占一整段频率，而是交错分布，让三种位置维度都能用到更连续的频率带。

Qwen3-VL 对视频时间的处理又和 Qwen2.5 不一样。processor 会根据视频 metadata 计算每个视觉帧/时间片的秒数，并在 prompt 中插入类似 `<1.5 seconds><|vision_start|>...<|vision_end|>` 的文本时间戳。源码里的 `get_rope_index` 甚至有注释说明：时间维 `t_index` 始终为 0，因为视频 temporal information 用 timestamps 编码。也就是说，Qwen3-VL 把一部分时间理解交给语言 token 的显式文本时间戳，而不是完全塞进视觉 RoPE 的时间坐标里。

MoE 版本的核心是 `Qwen3VLMoeTextSparseMoeBlock`。它先用一个 gate 产生 router logits，再 softmax，取 top-k expert，把 token 分派给少数专家。默认配置里能看到 `num_experts_per_tok=4`、`num_experts=60` 这类参数。白话说：总参数很大，但每个 token 只走一小部分专家，所以推理时的激活参数小于总参数。代价是路由负载均衡、专家并行、显存分布和部署复杂度都上升。

7. 关键模块逐个拆：processor、视觉塔、Merger、LLM 注入

`processor` 是很多人忽略但最容易出错的模块。它不仅做 resize/normalize，还会按照 `image_grid_thw.prod() // merge_size^2` 计算视觉 token 数，把文本里的一个 `<|image_pad|>` 扩展成很多占位符。Qwen3-VL 还会为每个视频帧加秒级 timestamp 文本。processor 错了，模型主体再正确也没用。

视觉塔是 ViT 变体，但不能按普通分类 ViT 理解。普通 ViT 最后可能只要 CLS 或全局池化；Qwen-VL 需要保留一串 patch token，给 LLM 做局部阅读。因此它要关心 patch size、temporal patch、grid_thw、cu_seqlens、window attention 和 rotary/pos embedding。

Merger 是跨模态接口的“插头转换器”。视觉塔隐藏维和 LLM 隐藏维往往不同，token 粒度也太细。Merger 把空间邻域组合起来，变成数量较少、维度合适的视觉 token。把它理解成一个 learnable pooling + projection，比理解成普通 linear 更准确。

LLM 注入阶段并不是 cross-attention，而是 embedding replacement：先得到文本 token embedding，再用 `image_mask` / `video_mask` 找到占位符位置，把这些位置替换成视觉 embedding。优点是实现和推理路径接近纯 decoder-only LLM；缺点是 token 对齐必须绝对正确。

8. 几个必须掌握的公式和复杂度

第一条是视觉 token 数。令 `P` 是 patch size，`M` 是 spatial merge size，输入 resize 后尺寸为 `H×W`，视频时间 patch 后为 `T`，则大致有：

Npatch=T⋅HP⋅WP,NLLM=NpatchM2N_{patch}=T\cdot \frac{H}{P}\cdot \frac{W}{P},\qquad N_{LLM}=\frac{N_{patch}}{M^2}Npatch​=T⋅PH​⋅PW​,NLLM​=M2Npatch​​

Qwen2/Qwen2.5 常见 `P=14, M=2`，所以单图约为 `H×W/784` 个 LLM 视觉 token。Qwen3-VL 常见 patch size 变为 16，`M=2` 时单图约为 `H×W/1024`。这也是为什么 Qwen3-VL 可以支持更高图像 token 上限，但仍必须靠预算控制。

第二条是 attention 复杂度。全局注意力对视觉 token 数近似二次：

Costfull∼O(N2),Costwindow∼O(K⋅Ws2)≈O(N⋅Ws)Cost_{full}\sim O(N^2),\qquad Cost_{window}\sim O(K\cdot W_s^2)\approx O(N\cdot W_s)Costfull​∼O(N2),Costwindow​∼O(K⋅Ws2​)≈O(N⋅Ws​)

这里 `W_s` 是窗口内 token 数，`K` 是窗口数。Window Attention 不是免费，它牺牲了每层跨窗口通信，所以需要少数全局层来补回来。这就是 `fullatt_block_indexes` 的意义：大多数层省算力，少数层做全局整合。

第三条是 MoE 激活成本。总专家数为 `E`，每个 token 选择 `k` 个专家，则每个 token 的 FFN 激活大致只走 `k/E` 的专家子集。当然真实成本还受专家大小、通信、batch、并行策略影响。

9. 常见误解：很多坑都在这些地方

误解一：动态分辨率等于原图不动。实际是按 token 预算和 patch/merge 约束 resize，只是比固定方图更尊重宽高比和细节。

误解二：视觉塔越强，LLM 就自然看懂。视觉特征必须被正确投影、正确占位、正确位置编码，语言模型还要经过训练学会使用这些 token。没有对齐训练，视觉特征只是一串外来向量。

误解三：Qwen2.5 的 Window Attention 只是加速。它同时改变了信息流：窗口层局部整合，全局层跨窗口整合。窗口大小和全局层位置会影响细粒度 OCR、跨区域推理和长图理解。

误解四：Qwen3-VL 的 timestamp 就是换个 prompt 文本。它和 M-RoPE 设计配套：源码里视频 t_index 固定为 0，时间信息显式变成文本 token，这会影响长视频问答的定位方式和可解释性。

误解五：DeepStack 等于把更多 token 塞进上下文。更准确地说，它把中间层视觉特征注入语言模型前几层的视觉位置，强化细节通道；它不应被理解成简单扩大上下文。

误解六：MoE 总参数越大就一定越慢。MoE 的关键是 activated parameters，不是 total parameters。但部署时通信、负载均衡和专家并行会带来新的系统复杂度。

15. 最后总结：你应该带走的判断框架

判断一个 Qwen-VL 模块时，先问它解决的是哪种瓶颈：token 数瓶颈、位置感瓶颈、细节保真瓶颈、长视频时间瓶颈、结构化输出瓶颈，还是推理/部署效率瓶颈。模块名字不同，但都能放进这个框架里。

Qwen2-VL 的重点是把动态图像/视频输入和 M-RoPE 稳定跑通；Qwen2.5-VL 的重点是把长视频、窗口注意力、动态时间和结构化输出做得更产品化；Qwen3-VL 的重点是用 DeepStack、Interleaved-MRoPE、timestamp、Thinking 和 MoE 提升细粒度理解、长上下文推理和大模型扩展效率。

读源码时不要被大模型名字吓住。抓住四个变量：`grid_thw`、`merge_size`、`position_ids`、`image/video token mask`。这四个变量贯穿输入、视觉塔、位置编码、LLM 注入和生成缓存。只要它们通了，整套实现就有了骨架。

真正落地时，最值得做的不是盲目换更大的模型，而是建立一套 shape/token/position 审计：每次输入的视觉 token 预算、位置编码、替换 mask、输出格式、坐标系都可检查。多模态模型的失败经常不是“不会推理”，而是某个下层对齐细节已经错了。

16. 补充：processor、视觉塔、Merger、LLM 的逐步处理逻辑

这一节专门补你要的“基础模块每一步干什么”。三篇知乎博客其实给了很完整的代码路径：Qwen2-VL 那篇把图片推理从 `apply_chat_template`、resize、patchify、占位符扩展、视觉塔 forward、LLM 替换讲了一遍；Qwen2.5-VL 那篇重点补了 Window Attention 和绝对时间编码；Qwen3-VL 那篇补了 processor 的时间戳文本插入、patch size 变化、绝对位置插值、DeepStack 多层注入和 MoE 语言模型。下面把它们合成一条从输入到输出的完整流水线。

16.1 先看总流水线：一张图不是直接喂给 LLM，而是先变成一串“视觉词”

白话版：用户发来的图片/视频，先被 processor 切成很多小块；视觉塔把每个小块变成向量；Merger 把相邻的小块打包，减少 token 数并投影到 LLM 的 hidden size；LLM 再把这些视觉向量当成特殊 token 读进去，像读一段夹着图像证据的文本一样生成答案。

messages
  -> apply_chat_template: 把对话变成带 <|vision_start|><|image_pad|><|vision_end|> 的文本
  -> process_vision_info / image_processor / video_processor: 读图、抽帧、resize、patchify
  -> processor.__call__: 根据 grid_thw 把 1 个 image/video 占位符扩成 N 个占位符
  -> tokenizer: 得到 input_ids / attention_mask
  -> vision tower: pixel_values -> patch embedding -> vision blocks -> visual hidden states
  -> PatchMerger: 每 2x2 个空间 patch 打包成 1 个 LLM 视觉 token
  -> LLM forward: embed_tokens 后，用 visual embeddings 替换 image/video 占位符位置
  -> get_rope_index / position_ids: 给文本、图片、视频 token 配位置
  -> decoder layers + lm_head: 预测下一个文本 token

这条链路里最容易出错的是 processor 和 LLM 接口之间的数量对齐：processor 扩展出来多少个 `<|image_pad|>`，视觉塔+Merger 就必须产出多少个视觉 embedding。少一个或多一个都不行，源码里会直接检查并报类似“image features and image tokens do not match”的错误。

16.2 Processor 第一步：把“用户消息”改写成模型能解析的模板

以 Qwen2-VL 博客里的 demo 为例，用户消息本来是一个列表：里面有一张图片和一句“Describe this image.”。`processor.apply_chat_template` 会先把它改写成 ChatML 风格文本，图片位置暂时不是图片本身，而是 `<|vision_start|><|image_pad|><|vision_end|>`。这一步的作用是告诉后面的 tokenizer 和模型：这里将来会有一段视觉 token。

注意，`<|image_pad|>` 一开始只有一个。它不是最终 token 数，只是一个“先占个坑”的标记。真正要占多少坑，要等图片 resize、patchify、merge 以后才能算出来。所以 processor 的逻辑分成两段：先放一个抽象占位符，再根据视觉网格把它扩成很多个占位符。

原始消息:
  user: [image, text]

套模板后:
  <|im_start|>user
  <|vision_start|><|image_pad|><|vision_end|>Describe this image.<|im_end|>
  <|im_start|>assistant

白话理解：这像是在一篇文章里先写“这里插图”，但还不知道这张图最终会占几页。等图像处理器算出图像会变成多少个视觉 token，再把“这里插图”扩成对应数量的空位。

16.3 Processor 第二步：resize 不是随便缩放，而是为了 patch 和 merge 对齐

Qwen2-VL 和 Qwen2.5-VL 的默认 patch size 是 14，spatial merge size 是 2，所以图片高宽要调整到 `14 * 2 = 28` 的倍数。Qwen3-VL 把 patch size 改成 16，merge size 仍常见为 2，所以 factor 变成 `16 * 2 = 32`。三篇博客都反复强调这个点：尺寸约束不是审美问题，而是为了后面切 patch 和 2x2 merge 不出零头。

resize 的约束通常有四个：高宽必须是 factor 的倍数；总像素数不能低于 `min_pixels`；总像素数不能超过 `max_pixels`；尽量保持原宽高比。极端长条图还会被拒绝，因为宽高比太夸张时，模型很难稳定处理。

factor=patch_size×merge_sizefactor = patch\_size \times merge\_sizefactor=patch_size×merge_size
Npatch=T×Hgrid×Wgrid,NLLM_vision=Npatchmerge_size2N_{patch}=T\times H_{grid}\times W_{grid}, \quad N_{LLM\_vision}=\frac{N_{patch}}{merge\_size^2}Npatch​=T×Hgrid​×Wgrid​,NLLM_vision​=merge_size2Npatch​​

白话理解：patch size 决定“一刀切多大”；merge size 决定“后面几块打包成一块”。如果图片尺寸不是 factor 的倍数，最后就会出现一排或一列 patch 凑不成 2x2 的包，Merger 处理就不整齐。

16.4 Processor 第三步：图片为什么会被复制成两个相同帧

Qwen2-VL 博客里讲得很细：Qwen2 系列用 3D Conv 处理视觉输入，卷积核的时间深度是 2，也就是 `temporal_patch_size=2`。为了让图片和视频走同一套视觉塔路径，单张图片会被复制成两个相同帧。这样图片也能被看成一个长度为 2 的极短视频。

这一步不是为了增加信息量，因为两帧是一样的；它是为了统一张量形状。视频天然有时间维，图片没有时间维。复制一份以后，图片也有了 `T=2` 的临时时间维，后面的 `Conv3d(3, hidden, kernel_size=(2, patch, patch), stride=(2, patch, patch))` 就能同时处理图片和视频。

单张图片:
  [C, H, W]

为了适配 temporal_patch_size=2:
  [2, C, H, W]   # 两个相同帧

patchify 后:
  grid_t = 2 // 2 = 1
  grid_h = resized_h // patch_size
  grid_w = resized_w // patch_size

白话理解：视觉塔是一台“每次吃两帧”的机器。图片只有一帧，不够吃，所以复制一帧凑成两帧。凑出来不是为了让模型看到新内容，而是为了让输入格式统一。

16.5 Processor 第四步：patchify 的 reshape/transpose 到底在整理什么

博客里最关键的一段是 patchify：先把 resize 后的图像转成 channel-first，再根据 `grid_t`、`grid_h`、`grid_w` reshape；然后 transpose，把将来要 merge 的相邻 2x2 patch 提前排到一起；最后 flatten 成 `pixel_values`。

这一步很多人只记住“切 patch”，但忽略了“提前按 merge 顺序排好”。Qwen2/Qwen2.5 的 processor 并不是随便把 patch 从左到右拉平，而是会把空间上相邻的 2x2 patch 放到一起，方便后面的 PatchMerger 直接 `view(-1, context_dim * 4)`。

概念化流程:
  patches: [T, C, H, W]
  grid_t = T // temporal_patch_size
  grid_h = H // patch_size
  grid_w = W // patch_size

reshape 成:
  [grid_t, temporal_patch_size, C,
   grid_h // merge_size, merge_size,
   grid_w // merge_size, merge_size,
   patch_size, patch_size]

transpose:
  把同一个 2x2 merge 组里的 patch 排到相邻位置

flatten:
  pixel_values: [grid_t * grid_h * grid_w, C * temporal_patch_size * patch_size * patch_size]

Qwen2-VL 博客里的具体例子是：resize 后图片大约为 2044x1372，patch size 为 14，所以 patch 数为 `1 * 146 * 98 = 14308`；因为 merge size 为 2，最终给 LLM 的视觉 token 数是 `14308 / 4 = 3577`。这解释了为什么 `input_ids` 里会突然多出几千个 `<|image_pad|>`。

16.6 Processor 第五步：把一个占位符扩成 N 个占位符

视觉处理器得到 `image_grid_thw` 后，processor 才知道这张图会生成多少个 LLM 视觉 token。核心公式是 `image_grid_thw[index].prod() // merge_length`，其中 `merge_length = merge_size ** 2`。然后它把文本中的一个 `<|image_pad|>` 临时替换成 N 个 `<|placeholder|>`，最后再统一换回 N 个 `<|image_pad|>`。

merge_length = image_processor.merge_size ** 2
num_image_tokens = image_grid_thw[index].prod() // merge_length

text = text.replace(
    "<|image_pad|>",
    "<|placeholder|>" * num_image_tokens,
    1,
)
text = text.replace("<|placeholder|>", "<|image_pad|>")

为什么不直接一开始放 N 个 `<|image_pad|>`？因为 N 取决于图片实际尺寸、resize 后尺寸、patch size、merge size、视频抽帧数。文本模板阶段还不知道这些。processor 必须先处理视觉输入，再回头改写文本。

到这一步，tokenizer 才真正开始把长文本转成 `input_ids`。所以最终 `input_ids` 的长度不是原 prompt 的文字长度，而是文字 token 数加上全部视觉占位符数。图片越大、视频帧越多，这个序列越长。

16.7 视频 processor：Qwen2.5 用绝对时间，Qwen3 把时间戳写进文本

Qwen2.5-VL 博客补充的关键点是：视频不能只知道“第几帧”，还要知道真实时间间隔。它在 `get_rope_index` 里引入 `second_per_grid_ts`，再结合 `tokens_per_second`，让时间维 position id 和真实秒数挂钩。比如同样是 8 帧，1 秒采 8 帧和 4 秒采 2 帧，不应该拥有完全一样的时间位置。

Qwen3-VL 博客则进一步说明：Qwen3 把原来的 T-RoPE 思路改成文本时间戳对齐。processor 会利用视频 metadata 里的帧索引和 fps 算出每个时间块的中心时间，然后构造类似 `<0.2 seconds><|vision_start|>...<|vision_end|>` 的文本片段。也就是说，时间不只是藏在 RoPE 的 t 轴里，还显式作为文本 token 出现在 LLM 输入里。

Qwen3-VL 视频占位符概念化:
  原始: <|video_pad|>

  展开后:
  <0.2 seconds><|vision_start|><|video_pad|> ... <|video_pad|><|vision_end|>
  <0.8 seconds><|vision_start|><|video_pad|> ... <|video_pad|><|vision_end|>
  ...

每一帧/时间块:
  frame_seqlen = video_grid_thw[index][1:].prod() // merge_length

白话理解：Qwen2.5 像是在视觉 token 的位置编码里写“这一块对应第几秒”；Qwen3 更像是在视频帧前直接贴一个字幕“0.2 seconds”。这样 LLM 在做长视频问答时，可以直接用文本方式引用时间点，事件定位也更自然。

16.8 视觉塔第一步：PatchEmbed 用 3D Conv 把像素块变成向量

processor 产出的 `pixel_values` 还是“像素块展开后的数值”，不能直接给 LLM。视觉塔第一步是 PatchEmbed。Qwen2/Qwen2.5 对应 `Conv3d(3, 1280, kernel_size=(2,14,14), stride=(2,14,14))`；Qwen3 对应 `Conv3d(3,1152,kernel_size=(2,16,16), stride=(2,16,16))`，并且 Qwen3 版本里带 bias。

Conv3d 的意思是：一次看 2 帧、14x14 或 16x16 的空间块，把这个小立方体投影成一个 hidden vector。它做的事情类似文本模型的 embedding 层：文本 token id 会查表变成向量，视觉 patch 会经过 3D 卷积变成向量。

Qwen2/Qwen2.5:
  pixel patch: [C * 2 * 14 * 14]
  PatchEmbed -> [vision_hidden=1280]

Qwen3:
  pixel patch: [C * 2 * 16 * 16]
  PatchEmbed -> [vision_hidden=1152]

白话理解：PatchEmbed 是“像素到视觉词向量”的翻译器。它不负责理解整张图，只负责把每个小块变成 Transformer 能继续处理的向量。

16.9 视觉塔第二步：位置编码告诉模型每个视觉词来自哪里

只把 patch 变成向量还不够，因为 Transformer 本身不知道第几个向量来自图片左上角还是右下角。Qwen2/Qwen2.5 主要使用视觉 RoPE / M-RoPE 体系，让每个视觉 token 带上空间位置；Qwen3 在视觉塔里还额外加了可学习的绝对位置编码，并通过 `fast_pos_embed_interpolate` 适配任意分辨率。

Qwen3 的绝对位置插值可以这样理解：模型内部有一个 48x48 的基础位置表，但输入图片可能是任意 HxW 网格。代码会把目标网格坐标映射回 48x48 基础网格，用双线性插值拿到位置向量，再重复到每个时间块，并按 merge 顺序重排。

版本视觉塔位置处理解决的问题
Qwen2-VL视觉 rotary position + M-RoPE 接入 LLM让图片/视频 token 有二维/三维位置感
Qwen2.5-VL沿用 M-RoPE，并在视频时间维加入 `second_per_grid_ts`让时间位置与真实秒数对齐
Qwen3-VL`fast_pos_embed_interpolate` + `rot_pos_emb` + Interleaved-MRoPE任意分辨率下保留空间位置，并让 t/h/w 频率分布更均匀

白话理解：PatchEmbed 告诉模型“这是什么样的小块”，位置编码告诉模型“这个小块在图里的什么地方、视频里的什么时候”。没有位置编码，OCR、表格、坐标定位、视频事件顺序都会明显受影响。

16.10 视觉塔第三步：cu_seqlens 限制注意力范围，避免不同图片混在一起

视觉塔 forward 里常见一个变量 `cu_seqlens`。它是 cumulative sequence lengths，也就是累计序列边界。假设 batch 里有多张图片或多个视频，所有 patch 会拼成一个长序列，但注意力计算时不能让第一张图的 patch 随便 attend 到第二张图的 patch。`cu_seqlens` 就是告诉 FlashAttention/SDPA：每个样本的起止边界在哪里。

概念化:
  image A patches: 0 ... 99
  image B patches: 100 ... 239

cu_seqlens = [0, 100, 240]

含义:
  attention 在 [0,100) 内部算一次
  attention 在 [100,240) 内部算一次
  不把 A 和 B 的视觉 patch 混在一个 attention 块里

白话理解：`cu_seqlens` 像是给拼接后的长队伍画分隔线。队伍看起来连在一起，但计算注意力时每张图/每个视频仍然是独立小组。

16.11 Qwen2 视觉塔：全局视觉注意力后直接 Merger

Qwen2-VL 的视觉塔流程最直：`patch_embed -> rot_pos_emb -> blocks -> merger`。博客里也指出，Qwen2-VL 没有很重的 Connector，视觉编码向量经过 PatchMerger 后直接进入语言模型。

Qwen2-VL visual forward:
  hidden_states = patch_embed(pixel_values)
  rotary_pos_emb = rot_pos_emb(grid_thw)
  cu_seqlens = build_boundaries_from(grid_thw)
  for block in vision_blocks:
      hidden_states = block(hidden_states, cu_seqlens, rotary_pos_emb)
  image_embeds = merger(hidden_states)

这说明 Qwen2-VL 的融合策略偏轻量：视觉塔负责把图像局部信息编码好，Merger 负责压缩和投影，LLM 负责统一推理。它没有在视觉和语言之间塞一个很复杂的跨模态模块。

16.12 Qwen2.5 视觉塔：Window Attention 先重排，再局部注意力，最后还原

Qwen2.5-VL 博客重点解释了 `get_window_index`。它先基于 `grid_thw` 算出 merge 后的 LLM 网格尺寸 `llm_grid_h = grid_h // spatial_merge_size`、`llm_grid_w = grid_w // spatial_merge_size`；然后按窗口大小给网格 padding；再把一个窗口内的索引排到一起；最后得到 `window_index` 和 `cu_window_seqlens`。

forward 时，hidden states 和 rotary position 都会按 `window_index` 重排。大多数视觉 block 使用 `cu_window_seqlens`，也就是只在窗口内部算 attention；少数 `fullatt_block_indexes` 层使用全局 `cu_seqlens`，负责跨窗口整合。Merger 后再用 `reverse_indices = argsort(window_index)` 把顺序还原。

Qwen2.5-VL visual forward:
  hidden_states = patch_embed(pixel_values)
  rotary_pos_emb = rot_pos_emb(grid_thw)
  window_index, cu_window_seqlens = get_window_index(grid_thw)

  hidden_states = group_by_window(hidden_states, window_index)
  rotary_pos_emb = group_by_window(rotary_pos_emb, window_index)

  for layer_num, block in enumerate(blocks):
      if layer_num in fullatt_block_indexes:
          cu = cu_seqlens          # 全局注意力
      else:
          cu = cu_window_seqlens   # 窗口注意力
      hidden_states = block(hidden_states, cu)

  hidden_states = merger(hidden_states)
  hidden_states = restore_original_order(hidden_states, window_index)

白话理解：全局注意力像让全班所有人互相交流，成本很高；窗口注意力像把学生分成小组讨论，便宜很多；少数全局层像全班代表再开会，把小组信息打通。Qwen2.5 的设计就是大部分时间小组讨论，偶尔全班交流。

16.13 Qwen3 视觉塔：去掉 Qwen2.5 的窗口主线，改成绝对位置插值 + DeepStack

Qwen3-VL 博客说得很明确：Qwen3 的结构变化较大，前一代 Qwen2.5-VL 的窗口注意力被抛弃，ViT 又更接近常见 ViT 结构；但它新增了更重要的 DeepStack。视觉塔不只输出最后一层 Merger 结果，还会在指定层，比如 `[8,16,24]`，取出中间视觉特征，经过 `deepstack_merger_list` 投影，后面注入 LLM 的浅层 hidden states。

Qwen3-VL visual forward:
  hidden_states = patch_embed(pixel_values)
  hidden_states = hidden_states + fast_pos_embed_interpolate(grid_thw)
  rotary_pos_emb = rot_pos_emb(grid_thw)
  cu_seqlens = build_boundaries_from(grid_thw)

  deepstack_feature_lists = []
  for layer_num, block in enumerate(blocks):
      hidden_states = block(hidden_states, cu_seqlens, position_embeddings)
      if layer_num in deepstack_visual_indexes:
          deepstack_feature = deepstack_merger_list[k](hidden_states)
          deepstack_feature_lists.append(deepstack_feature)

  final_visual_embeds = merger(hidden_states)
  return final_visual_embeds, deepstack_feature_lists

白话理解：Qwen2/Qwen2.5 像是只把视觉塔最后一层的总结交给 LLM；Qwen3 还把中间层的细节也分批送进去。底层视觉层更保留边缘、纹理、局部形状；高层视觉层更偏语义。DeepStack 的目的就是别让 LLM 只看到最后的抽象总结，而是也能拿到不同层次的视觉证据。

16.14 Merger：为什么要把 2x2 patch 压成 1 个视觉 token

Merger 的核心目的有两个：第一，把视觉 token 数减少到 LLM 可承受的范围；第二，把视觉塔 hidden size 投影到 LLM hidden size。Qwen2/Qwen2.5 的 Merger 结构大致是 `ln_q -> view(-1, context_dim * 4) -> Linear -> GELU -> Linear(dim)`。这里的 4 就来自 `merge_size^2 = 2^2`。

在 Qwen2/Qwen2.5 里，视觉塔 hidden size 常见为 1280，LLM hidden size 为 3584。Merger 会把 4 个 1280 维 patch 拼成 5120 维，再通过 MLP 变成 3584 维。Qwen3 里视觉 hidden size 是 1152，4 个拼成 4608，再投影到 4096 维语言模型空间。

Qwen2.5-VL4 个相邻视觉 patch1280 * 4 = 51203584Qwen2.5 LLM

白话理解：Merger 像把相邻 2x2 的小图块装进一个文件袋，再贴上 LLM 能读懂的标签。它不是简单平均，也不是纯裁剪，而是一个可学习的打包器：模型可以自己学哪些局部信息应该保留、哪些可以压缩。

16.15 LLM 接入第一步：先得到普通文本 embedding

进入 `Qwen*_VLForConditionalGeneration.forward` 后，如果没有外部传入 `inputs_embeds`，模型会先用语言模型的 embedding 表把 `input_ids` 转成普通 token embedding。此时 `<|image_pad|>` 和 `<|video_pad|>` 也只是普通特殊 token 的 embedding，还没有真正视觉内容。

if inputs_embeds is None:
    inputs_embeds = embed_tokens(input_ids)

此时:
  文本 token -> 文本 embedding
  <|image_pad|> -> 一个普通特殊 token embedding
  <|video_pad|> -> 一个普通特殊 token embedding

白话理解：这一步像先把整篇文章排版好，图片位置也放了占位框，但框里还没有真正图片内容。

16.16 LLM 接入第二步：视觉塔算出 image_embeds / video_embeds

如果 `pixel_values` 不为空，模型调用 `get_image_features` 或直接 `self.visual(pixel_values, grid_thw=image_grid_thw)` 得到 `image_embeds`。如果 `pixel_values_videos` 不为空，同样得到 `video_embeds`。Qwen3 会额外拿到 `deepstack_image_embeds` / `deepstack_video_embeds`。

这里有一个关键点：视觉特征的数量已经是 Merger 后的数量，不再是原始 patch 数。也就是说，如果 processor 把一个图片占位符扩展成 3577 个 `<|image_pad|>`，视觉塔+Merger 最终就必须输出 3577 条 image embedding。

16.17 LLM 接入第三步：用 mask 把占位符 embedding 替换成视觉 embedding

Qwen2 的代码里直接用 `image_mask = input_ids == image_token_id`，然后 `inputs_embeds[image_mask] = image_embeds`。Qwen2.5/Qwen3 的实现更封装，会先通过 `get_placeholder_mask` 检查数量，再用 `masked_scatter` 替换。逻辑是一回事：找到所有 image/video 占位符位置，把这些位置的 embedding 换成视觉塔输出。

image_mask = (input_ids == image_token_id)
video_mask = (input_ids == video_token_id)

检查:
  image_mask 对应的元素数量 == image_features.numel()
  video_mask 对应的元素数量 == video_features.numel()

替换:
  inputs_embeds = inputs_embeds.masked_scatter(image_mask_expanded, image_embeds)
  inputs_embeds = inputs_embeds.masked_scatter(video_mask_expanded, video_embeds)

白话理解：原来文章里有 3577 个空白图片框，现在把 3577 个视觉向量按顺序塞进去。塞完以后，LLM 看到的就是一整串 embedding：前面可能是 system prompt，中间夹着视觉 embedding，后面是用户问题。

16.18 LLM 接入第四步：get_rope_index 给混合序列分配位置

文本模型原本只需要一维位置：第 0 个 token、第 1 个 token、第 2 个 token。多模态输入不够，因为视觉 token 有空间和时间结构。`get_rope_index` 的任务就是给文本、图片、视频混排后的序列分配三路位置：time、height、width。

Qwen2/Qwen2.5 的逻辑是：纯文本段三路位置都一样；遇到图片段，就根据 `image_grid_thw` 构造 h/w 网格，time 通常不发挥真实视频时间作用；遇到视频段，就根据 `video_grid_thw` 构造 t/h/w。Qwen2.5 多了 `second_per_grid_ts`，让 t 轴按真实秒数拉开。

Qwen3 的逻辑发生变化：源码注释里明确说 Qwen3VL 使用 timestamps 而不是 absolute time position ids。也就是说，视频时间被写成文本时间戳插入序列，视觉 RoPE 里的 `t_index` 在相应处理下不再承担同样的真实时间建模责任。

16.19 LLM 主体：视觉 token 已经混进输入，后面就是 decoder-only 生成

完成 embedding replacement 和 position ids 后，后面的 LLM 主体基本就是 decoder-only Transformer：self-attention、MLP/MoE、RMSNorm、残差连接、最后 `lm_head` 输出词表 logits。区别在于输入 embedding 中一部分来自文本 embedding 表，一部分来自视觉塔输出。

Qwen2/Qwen2.5 的语言模型是 dense LLM；Qwen3-VL-MoE 版本的语言模型里有 sparse MoE block，router 会为每个 token 选择部分专家。白话说，总参数可以很大，但每个 token 激活的专家只是一部分，所以“总参数”和“每 token 推理计算量”不是一回事。

生成时还有一个重要工程点：视觉塔通常只在 prefill 阶段跑一次。第一步已经把完整 prompt，包括视觉 token，都送入模型并建立 KV cache；后续每生成一个新 token，只需要把新文本 token 接着喂进去，不会每一步都重新编码图片。否则生成 100 个 token 就要重复跑 100 次视觉塔，成本会非常高。

prefill 阶段:
  编码图片/视频
  替换视觉占位符
  计算完整 prompt 的 KV cache

decode 阶段:
  每次只输入上一步生成的新 token
  复用 past_key_values
  根据 rope_deltas / cache_position 延续位置

16.20 DeepStack 在 LLM 里到底怎么用

Qwen3-VL 博客把 DeepStack 比作多层视觉特征注入。源码里，视觉塔在若干中间层取出 hidden states，经过 `deepstack_merger_list` 变成 LLM hidden size 的视觉特征列表；语言模型 forward 里带着 `deepstack_visual_embeds`，在前几层通过 `_deepstack_process` 注入到对应视觉位置。

这和普通 image embedding replacement 不一样。普通 replacement 只发生在 LLM 输入层：把占位符 embedding 换成最终视觉 embedding。DeepStack 是在 LLM 的若干层内部继续补充视觉特征，相当于让浅层/中层 LLM 也能直接接触来自 ViT 中间层的视觉细节。

白话理解：普通方式像只在开头给 LLM 一份图片摘要；DeepStack 像在 LLM 阅读过程中，隔几层又递给它一份不同粒度的视觉笔记。这样对 OCR、细粒度定位、复杂图文对齐更有帮助。

16.22 如果你自己调试，按这个顺序打印 shape

多模态模型最常见的问题不是模型“不聪明”，而是下层 shape、token 数、位置、mask 已经错了。建议你从 processor 到 LLM 一路打印下面这些变量。只要这些对不上，后面 loss 正常下降也可能是在学错误对齐。

Processor 侧:
  text after apply_chat_template
  resized image/video size
  pixel_values.shape
  image_grid_thw / video_grid_thw
  expected_visual_tokens = prod(grid_thw) // merge_size**2
  input_ids.shape
  count(input_ids == image_token_id)
  count(input_ids == video_token_id)

Vision 侧:
  after patch_embed: hidden_states.shape
  rotary_pos_emb.shape / position_embeddings shape
  cu_seqlens / cu_window_seqlens
  after merger: image_embeds.shape / video_embeds.shape
  deepstack_visual_embeds shapes, if Qwen3

LLM 侧:
  inputs_embeds.shape
  special_image_mask.sum()
  special_video_mask.sum()
  position_ids.shape
  rope_deltas
  past_key_values after prefill

最实用的自检公式是：`count(input_ids == image_token_id)` 必须等于 `image_embeds.shape[0]`；`count(input_ids == video_token_id)` 必须等于 `video_embeds.shape[0]`。如果是 Qwen3，还要额外确认 timestamp 文本是否真的插入、每个时间块的 `frame_seqlen` 是否和 `video_grid_thw` 对得上。

16.23 三篇博客怎么合成同一条主线

三篇博客不是三套互不相关的笔记，而是在同一条多模态 forward 链路上分别补了不同薄弱环节。Qwen2-VL 文章把最基础的图片输入链路讲清楚：模板、视觉预处理、patchify、占位符扩展、视觉塔、Merger、LLM 替换。Qwen2.5-VL 文章把长图长视频时的视觉塔成本和时间建模补上：窗口注意力、`cu_window_seqlens`、少数全局层、`second_per_grid_ts`。Qwen3-VL 文章再把更细粒度的视觉细节和更长视频时间对齐补上：32 倍数 resize、`fast_pos_embed_interpolate`、timestamp 文本插入、DeepStack、Interleaved-MRoPE 和 MoE。

来源它重点解释了哪一段这段在总链路里的位置应该记住的核心变量
Qwen2-VL 博客`apply_chat_template`、`process_vision_info`、图片复制两帧、patch reshape/transpose、`image_grid_thw`、PatchMerger、LLM 占位符替换从外部图片到 LLM 能读的视觉 token，是最基础的主干`pixel_values`、`grid_thw`、`merge_size`、`image_token_id`、`image_embeds`
Qwen2.5-VL 博客`get_window_index`、`cu_window_seqlens`、`fullatt_block_indexes`、`reverse_indices`、`second_per_grid_ts`、动态 FPS视觉塔内部如何降计算量，以及视频时间位置如何变得更真实`window_index`、`cu_window_seqlens`、`cu_seqlens`、`tokens_per_second`
Qwen3-VL 博客`fast_pos_embed_interpolate`、`deepstack_visual_indexes`、`deepstack_merger_list`、timestamp 文本、`masked_scatter`、MoE router视觉塔输出不再只是一份最终摘要，而是带中间层细节和显式时间文本进入 LLM`pos_embeds`、`deepstack_visual_embeds`、`frame_seqlen`、`rope_deltas`、`router_logits`

所以读的时候不要按“版本更新日志”来背。更好的读法是沿着一次推理走：先问 processor 生成了多少坑位，再问视觉塔生成了多少视觉向量，再问 Merger 是否把数量和维度压到 LLM 能接收，再问 LLM 是否把这些向量准确塞回占位符，最后才看位置编码、DeepStack 和 MoE 怎么增强这条主干。

16.24 一次图片 forward 的逐步账本：每一步输入什么、输出什么

下面把 Qwen2-VL 博客里的图片 demo 拆成更细的账本。你可以把它理解成模型内部的物流单：每一步只做一件事，并把货物交给下一步。

0. 用户消息
   输入: messages = [{role: user, content: [image_url, text]}]
   输出: 仍是 Python list/dict，还不是 token

1. apply_chat_template
   输入: messages
   动作: 插入 ChatML 标记，并把图片位置写成 <|vision_start|><|image_pad|><|vision_end|>
   输出: text 字符串
   白话: 先在文章里写“这里以后要放图”

2. process_vision_info
   输入: messages
   动作: 读取图片 URL/路径，整理成 image_inputs；视频同理整理成 video_inputs
   输出: image_inputs, video_inputs
   白话: 把外部文件先搬到视觉处理器能读的位置

3. image_processor.preprocess
   输入: image_inputs
   动作: resize 到 factor 倍数，normalize，转 channel-first
   输出: processed_images
   白话: 把图片尺寸和数值范围整理干净

4. 图片补 temporal 维
   输入: processed_images.shape[0] == 1
   动作: np.tile(..., temporal_patch_size=2)
   输出: 两个相同帧
   白话: 图片伪装成一个两帧小视频，统一走 3D Conv

5. patchify + merge-order reshape
   输入: [T, C, H, W]
   动作: 按 patch_size 切块，并通过 reshape/transpose 让 2x2 邻近 patch 靠在一起
   输出: pixel_values, image_grid_thw
   白话: 不只是切小块，还提前把将来要打包的邻居排好队

6. placeholder expansion
   输入: text, image_grid_thw
   动作: num_image_tokens = prod(grid_thw) // merge_size**2
   输出: 展开后的 text，里面有 N 个 <|image_pad|>
   白话: 根据图片实际会产生多少视觉 token，在文本里挖出同样数量的坑

7. tokenizer
   输入: 展开后的 text
   动作: 文本转 token id
   输出: input_ids, attention_mask
   白话: 现在视觉坑位也已经变成真实 token id

8. visual.patch_embed
   输入: pixel_values
   动作: Conv3d 把每个像素块投影成视觉 hidden vector
   输出: vision hidden states
   白话: 像素块变成“视觉词向量”

9. visual blocks
   输入: vision hidden states + position embeddings + cu_seqlens
   动作: 自注意力和 MLP 建立局部/全局视觉关系
   输出: 上下文增强后的视觉 hidden states
   白话: 每个小块不再孤立，开始知道周围小块是什么

10. PatchMerger
    输入: 每 4 个相邻视觉 patch hidden states
    动作: view 拼接 -> LayerNorm/MLP -> 投影到 LLM hidden size
    输出: image_embeds
    白话: 把 2x2 小块打包成一个 LLM 能读的视觉 token

11. LLM embedding replacement
    输入: input_ids, image_embeds
    动作: 找到 <|image_pad|> 的位置，把普通 token embedding 换成 image_embeds
    输出: inputs_embeds
    白话: 把空图片框逐个填成真实视觉向量

12. decoder-only generation
    输入: inputs_embeds, position_ids, attention_mask
    动作: prefill 建 KV cache，随后自回归生成文本
    输出: generated_ids
    白话: 后面就像普通 LLM 生成，只是上下文里已经夹进了视觉证据

这份账本的关键是“数量守恒”：第 6 步挖了 N 个视觉坑，第 10 步就必须产出 N 个 image embedding，第 11 步才能一一填进去。Qwen-VL 的很多 runtime error 都不是注意力层本身错，而是这条数量守恒链在 processor 或 Merger 附近断了。

16.25 一次视频 forward 的逐步账本：Qwen2.5 和 Qwen3 的分歧在哪里

视频路径和图片路径共用很多部件，但多了时间问题。Qwen2.5 的重点是把真实秒数写进时间位置编码；Qwen3 的重点是把时间戳直接写进文本序列。二者都想解决同一个问题：模型不能只知道“这是第几个视觉块”，还要知道“它大概发生在第几秒”。

步骤Qwen2.5-VL 做法Qwen3-VL 做法白话解释

视觉占位符一个 `<|video_pad|>` 根据 `video_grid_thw` 展开成大量视频 token 坑位按每个时间块构造 `<seconds> + vision span`，每帧/时间块有自己的视觉 spanQwen3 不只是挖坑，还给每段视觉 token 前贴时间标签
时间建模`second_per_grid_ts * tokens_per_second` 进入 `get_rope_index` 的 t 轴源码注释强调 timestamp 文本承担时间信息，视觉 `t_index` 不再按旧式绝对时间承担全部责任Qwen2.5 更像在坐标里写秒数，Qwen3 更像在输入文本里写字幕

Qwen2.5 视频时间主线:
  video_grid_thw -> get_rope_index(...)
  second_per_grid_ts -> temporal position ids
  tokens_per_second -> 时间位置粒度

Qwen3 视频时间主线:

  for each frame/time block:

      text += vision_start + placeholder * frame_seqlen + vision_end

这就是为什么 Qwen3 的视频 processor 更像“给每段视频帧加字幕”。模型后面回答“第 12 秒发生了什么”时，语言模型可以直接在文本 token 中看到 `<12.0 seconds>` 这种锚点，而不是完全依赖隐藏在 RoPE t 轴里的时间坐标。

16.26 Qwen2.5 Window Attention 的实际执行顺序

Qwen2.5 的 Window Attention 不是简单把 attention mask 改小，而是先重排 token，再按窗口算 attention，最后还原顺序。博客里给出的 `get_window_index` 和 forward 代码非常关键，因为它解释了为什么 `reverse_indices` 必须存在。

1. hidden_states = patch_embed(pixel_values)
2. rotary_pos_emb = rot_pos_emb(grid_thw)
3. window_index, cu_window_seqlens = get_window_index(grid_thw)

4. hidden_states reshape 成 [merge 后 token 组, spatial_merge_unit, hidden]
5. hidden_states = hidden_states[window_index]
6. rotary_pos_emb = rotary_pos_emb[window_index]

7. for layer_num, block in blocks:
       if layer_num in fullatt_block_indexes:
           cu_seqlens_now = cu_seqlens          # 全局注意力
       else:
           cu_seqlens_now = cu_window_seqlens   # 窗口内注意力
       hidden_states = block(hidden_states, cu_seqlens_now, position_embeddings)

8. hidden_states = merger(hidden_states)
9. reverse_indices = argsort(window_index)
10. hidden_states = hidden_states[reverse_indices]

白话解释：先把同一个窗口里的 token 排到连续位置，这样 FlashAttention/SDPA 就能按一段一段的 `cu_window_seqlens` 高效计算。多数层只看窗口内，便宜；少数层看全局，负责跨窗口信息流。Merger 后必须用 `reverse_indices` 把顺序恢复，否则视觉 embedding 填回 LLM 占位符时就会错位。

16.27 Qwen3 DeepStack 和 MoE 在 forward 里各自干什么

Qwen3 的复杂度主要来自两条增强线。第一条是 DeepStack，它增强视觉细节；第二条是 MoE，它增强语言模型规模和推理能力。它们不是同一件事：DeepStack 管“视觉证据怎么多层进入 LLM”，MoE 管“LLM 每个 token 走哪些专家”。

机制发生位置输入动作输出白话
普通视觉 replacementLLM 输入层之前`input_ids`、最终 `image_embeds/video_embeds`用 mask 或 `masked_scatter` 替换视觉占位符`inputs_embeds`把图片内容塞进文本序列的空位

MoE语言模型 MLP 子层当前 token hidden staterouter 选 top-k experts，专家 MLP 处理后加权合并token 的 FFN 输出不是所有专家都跑，每个 token 只走一部分专家
Qwen3 forward 概念顺序:
  final_visual_embeds, deepstack_visual_embeds = visual(pixel_values, grid_thw)
  inputs_embeds = replace_placeholders(input_ids, final_visual_embeds)

  for layer_idx, decoder_layer in enumerate(language_layers):
      hidden_states = decoder_layer.self_attn(hidden_states, position_embeddings, cache)
      hidden_states = maybe_deepstack_process(layer_idx, hidden_states, deepstack_visual_embeds)
      hidden_states = decoder_layer.mlp_or_moe(hidden_states)
      # MoE 只影响语言层 FFN 计算，不负责视觉 token 数量对齐

所以不要把 DeepStack 理解成“又加了一堆图片 token”。它更像在相同视觉位置上补充中间层视觉特征。也不要把 MoE 理解成“图像专家”。Qwen3-VL-MoE 里的 MoE 主要是语言模型稀疏 FFN 路由，视觉信息已经通过 replacement 和 DeepStack 进入 hidden states，MoE 只是继续处理这些混合后的 token 表示。

16.29 一句话串起来

processor 负责“准备坑位和像素块”：把外部图片/视频整理成 `pixel_values + grid_thw`，同时把文本里的一个视觉占位符扩成对应数量的占位符；视觉塔负责“看局部”：把每个 patch 编成视觉向量，并通过位置编码和 attention 建立空间/时间关系；Merger 负责“打包翻译”：把相邻视觉 patch 压成更少的 LLM 视觉 token，并投影到语言模型维度；LLM 负责“统一阅读和生成”：把视觉 token 塞进文本序列，用多模态位置编码保持顺序和位置，最后自回归生成答案。Qwen2 是把这条链路跑通，Qwen2.5 是让长视频/高分辨率更省更准，Qwen3 是把时间戳、DeepStack 和更大的语言模型能力叠上去。
